    Decision Policy

    Fixed rules validate the agents’ recommendation before Argo can act.

    • At least 30 requests per revision and fresh evidence (120-second expiry).
    • Hold when required evidence is missing or limitations remain unresolved.
    • Enforce error and latency safety limits before GO.
    • Production promotion requires human approval (HITL).

    Human approval rechecks these rules; it cannot override missing or stale evidence or hard safety limits.

    EXTENDED FLOW
    Human-in-the-loop (HITL)
    1. 1 / Select Production / approvalUse a healthy candidate at an active gate with fresh samples. Run an investigation explicitly.
    2. 2 / Separate recommendation from authorityShow an eligible agent GO recommendation held as effective HOLD because Decision Policy requires approval.
    3. 3 / Approve with fresh evidenceSelect Approve promotion. Decision Policy rechecks eligibility, then Argo consumes the effective GO. A later Production gate needs a fresh investigation and approval.
    Decision Policy
    Implemented as deterministic Java/Quarkus rules in DecisionPolicy.java. Requires 30 requests per revision and fresh evidence; withholds GO for missing evidence or unresolved limitations; enforces error and latency limits; and requires eligible Production promotions to receive human approval. Approval cannot override these safeguards.
    04 / Missing evidence: where automation must stop
    Enterprise context: HTTP metrics stay green during a collector outage, telemetry misconfiguration, or evidence-access problem. Required dependency observations are unavailable, so the platform cannot justify promotion.
    Show: use a healthy v2 candidate at an active gate with no slowdown, at least 30 requests per cohort, and Development / no approval. Select Extended → Missing evidence and investigate. In Evidence explorer, compare healthy HTTP metrics with the empty trace observations and missing-evidence entry; show the effective HOLD and saved policy reason.
    Say: “The dashboard is green, but our required trace evidence is unavailable. The platform holds rather than turning uncertainty into permission. We restore evidence and reassess.”
    Recover: select Healthy release, confirm the same active candidate, and investigate again. The scenario withholds evidence in that investigation; it does not stop or repair Jaeger. Human approval cannot override a missing prerequisite. A complete eligible Development investigation can produce GO; Production still requires approval.
    Attendee insight: absence of evidence is not evidence of safety. HOLD for missing information differs from NO-GO for an evidenced regression.

    ENTERPRISE CONTEXT AND PRESENTER INSIGHTS
    02 / Shared slowdown: did the release cause it?
    Illustrative enterprise case: a retailer deploys checkout while its shared inventory database develops contention. Both stable and canary become slow. Shared identity-provider, network, and downstream API incidents can produce similar patterns.
    Show: Evidence explorer → Stable and canary p95, then Dependency Investigator, evidence references, limitations, and Recommendation → Decision Policy. Similar latency supports a shared-issue hypothesis; it does not prove root cause. Read the actual HOLD reason rather than assuming the agents confirmed the cause.
    Say: “Customers are slow on both revisions. We hold exposure, investigate the shared dependency, and require fresh healthy evidence before increasing traffic.”
    Use the wait: show frozen findings during the 60-second recovery window. The fault lasts 25 seconds; observe Checkout pods during the amber countdown to see roughly 650 ms added latency. After expiry, current logs can be fast while the frozen p95 remains high. Investigate recovery again at 10%, then at 50%.
    Enterprise value: avoid incorrect release attribution while retaining the safety stop. Live output can vary; explain an actual NO-GO if that is what the model returns.
    Google SRE: shared failure domains in canary releases
    03 / Hidden retries: what does success cost?
    Illustrative enterprise case: an SDK or retry-configuration change repeats inventory API calls until checkout succeeds. HTTP success and latency stay healthy while downstream connections, CPU, capacity, and API quota are consumed.
    Show: Evidence explorer → Inventory attempts / checkout: stable about 1×, v3 about 5×. Inspect Dependency Investigator retry evidence and Release Analyst runbook context. The recommendation summary explains NO-GO; the policy reason may only confirm that the recommendation was accepted.
    Say: “The HTTP response succeeds, but each checkout makes five times the inventory calls. Increasing traffic would spread that regression, so we stop the candidate before capacity is exhausted.”
    Scale example: at a hypothetical 1,000 checkouts/second, full v3 adoption means about 5,000 inventory attempts/second instead of 1,000; an exact 10% share already means about 1,400. These are illustrative calculations; the demo traffic split is approximate.
    Enterprise value: detect a regression that basic HTTP checks miss. Valid retries are useful; evidence-backed candidate-specific amplification is the concern. The 30-request minimum is an evidence prerequisite, not a retry limit or a hard retry threshold in Decision Policy.
